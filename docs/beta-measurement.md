# Beta measurement and review

This measures a visit, not a person. Reloading creates a new random, in-memory visit ID; there are no analytics cookies, browser storage, replay, autocapture, or cross-visit identity. The endpoint accepts only strict, finite event fields; it does not accept birth details, free text, URLs, coordinates, timezone, resolver data or snapshots. The browser sends at most 250 events per visit. The public endpoint is unauthenticated: origin checks and bounded payloads do not prevent spoofed or high-volume traffic, so exclude suspicious data and apply platform-level controls if abuse occurs.

## What is counted

Entry starts on the first edit, completes when resolved input is accepted, and its time to the first usable chart ends at the first accepted calculation. Recalculations do not produce another first-chart time. Resolver and calculation failures use finite categories without error text. Count starts without observed completion as **incomplete or unknown**, not confirmed abandonment: users may still be active or delivery may be lost. Define a cohort window and an observation grace period before reporting.

Eligibility is emitted once as soon as a usable personal chart or available help qualifies. The numerator is eligible visits with at least one observed explanation opening; zero-opening visits remain in the denominator. A system-help opening is an explanation. The first insight records its finite identity and elapsed milliseconds since eligibility. A selection, repeated selection, navigation, pan and zoom are separate interaction categories; total openings and distinct explanation identities per visit are separate measures. Exposure means the relevant surface was available, while feature use means it was activated. Device is based on viewport width and system describes the accepted chart, not an in-flight request. Custom is reported separately. Events use an ephemeral visit ID and a unique event ID for deduplication.

Events are sent immediately, with keepalive as best effort. Blocking, offline use, termination, sampling, export truncation and retention can lose events; observed counts are lower bounds and rates can be biased. First-insight records or openings without an observed eligibility event do not enter the eligible numerator; orphan openings are reported separately. More than 15 interactions per chart visit is a working question for Product, not a gate or proof of learning.

## Collect and report

The configured collection path is the existing Cloudflare Workers Logs: the same-origin endpoint validates each small event, then emits a single structured `event_source: natal_explorer_measurement_v1` record. The Worker configuration requests full sampling, disables invocation logs, and requests query-string redaction. Custom event records can still carry platform-generated metadata; disabling invocation logs is not proof that all request metadata is absent. Before treating deployed collection as privacy-accepted, inspect the actual effective environment configuration, sampling, emitted metadata, access controls, retention and export behavior. The local packaged-Worker synthetic run is not evidence that deployed collection works.

1. In the intended Worker environment, choose Observability events/query builder, select the correct environment and a stated time window, and filter for `natal_explorer_measurement_v1`. Verify the actual nested field names using an authorized synthetic event; do not assume all log views have identical shapes. Ensure the window includes the agreed grace period and all pages of results. Check effective sampling and retention for the account, and export before expiry.
2. Export filtered JSON or newline-delimited JSON into a restricted temporary location. Export envelopes can contain request metadata, so restrict access, avoid committing or sharing the raw export, and delete it after processing. The report scans object envelopes and JSON-encoded messages, extracts only marked events, validates each against the same strict schema, and deduplicates event IDs. Unsupported export shapes require inspection and adaptation before any reporting claim.
3. Run `bun scripts/measurement-report.ts /path/to/filtered-export.json '2026-01-01 to 2026-01-31 UTC' '48 hours after cohort end'`. The window and grace labels are supplied by the operator; the script does not enforce or filter them. Verify the export covers that cohort and grace before interpreting output. The report includes funnel, eligible numerator and orphans, feature exposure/use, opening totals, distinct identities, first identity and latency, interaction categories, failure counts and device/system segments. Conversion is grouped by the device/system on the eligibility event; feature activity and failures are grouped by the device/system on each event. A visit that changes system can therefore appear in multiple activity segments. `chartUsableMs` is the initial entry-to-chart duration; `firstInsightMs` is from eligibility.
4. `wrangler tail` can inspect a controlled live synthetic event in the correct authorized environment; it is a live feed, may sample and is not a historical export. Do not include birth information in URLs or console logs. The local Worker query/export used during development demonstrated one synthetic browser journey and the report path only; deployed tail, stored export, field shape and completeness remain unverified until separately tested in an authorized candidate environment.

The platform's retention and effective sampling can vary by plan and settings. Capture those facts with each report. Any longer-lived sanitized export requires an explicit owner, access policy and retention decision; do not assume indefinite automatic storage. Event IDs permit deduplication but do not authenticate visitors or guarantee exactly-once delivery.

## Post-beta Product review template

- **Cohort / window / grace / environment:**
- **Collection completeness, effective sampling, retention and known gaps:**
- **Entry:** observed starts, completions, incomplete/unknown, first chart timing, failure categories and device/system breakdown.
- **First insight:** eligible visits including zero-open visits; eligible visitors with an observed opening; orphan openings; first kinds/identities and time distribution.
- **Exploration:** feature exposures vs users, total interactions by category, opening totals, distinct explanations per visit and repeat exploration. Compare the working >15-interaction question without treating it as a release threshold.
- **Participant feedback gathered outside the app:** understanding, usefulness, confusion and self-reported returns. Record method and uncertainty; no in-app survey is added.
- **What remains unmeasured:** verified first-time viewers, actual cross-visit retention and unreported return behavior. Keep self-reported returns separate from instrumented within-visit results.
- **Decisions and questions:** learning to investigate, changes to test, and implications for later free/paid decisions. Do not claim beta findings before data exists.
