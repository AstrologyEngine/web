# Ordinary chart initialization: calculation contract

Research for [Specify ordinary chart initialization in the calculation library](https://github.com/AstrologyEngine/web/issues/8), under [Port the plugin UI into a standalone astrology explorer](https://github.com/AstrologyEngine/web/issues/5). Checked 2026-11-07. Planning only; no runtime, website or library implementation.

## Finding and source identity

**Existing library and shipped browser capabilities suffice. No library calculation change or new astronomical API is required to initialize this ordinary chart.** The website needs a host adapter that captures an instant, obtains the city result, constructs consistent chart metadata, and submits the same worker request used for edited birth details. This conclusion follows from the explicit-input Rust and Wasm APIs below, not from the name “birth chart.”

Live GitHub identifies the library as [`AstrologyEngine/library`](https://github.com/AstrologyEngine/library), default branch `main`, at `b2bd547728f31a951a1afd78dfaa94225d8c152f`. The plugin already pins this exact revision. The sibling library checkout was stale at `71350f0889c3b5e1585935d2017c97efe0bb5848`; its older MIT manifest and `calculate_configured_chart` API must not be treated as the current contract. Current source has MPL-2.0 licensing and a unified `calculate_chart` API. Sources: [current Cargo manifest](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/Cargo.toml), [current chart API](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/chart.rs), [plugin provenance](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/docs/calculation-provenance.md).

The plugin source inspected is `8446c7b1388349a28daaabf27f13096b61142271`. Its shipped source archive agrees with the live pinned API for chart input and design search. The shipped source archive is a separate packaging artifact from the original upstream commit tarball expected by `scripts/rebuild-engine.sh`; their hashes are not interchangeable.

## Explicit runtime contract

The current Rust API is `calculate_chart(&Ephemeris, ChartInput { epoch, location, house_system, zodiac }) -> Result<ChartValues, CalculationError>`. `Location` contains latitude/longitude in degrees; valid ranges are [-90,90] and [-180,180]. Longitude is east positive (the sidereal-angle formula adds it). The public Wasm wrapper accepts caller-supplied dataset bytes and JSON with these fields:

| Input                   | Required meaning                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `instant`               | `{ scale: "utc", value: "YYYY-MM-DDTHH:mm:ssZ" }`, or finite `{ scale: "et", value: seconds }` for engine ET replay      |
| `latitude`, `longitude` | Explicit geographic coordinates of the resolved city or edited place                                                     |
| `house_system`          | `whole-sign`, `equal`, or `placidus`                                                                                     |
| `configuration`         | Explicit reference (`tropical`, `fagan-bradley`, `true-sky`), divisions (`equal`, `constellation`), and Ophiuchus choice |

UTC parsing requires an explicit `Z` or ` UTC` suffix. Never pass local wall-clock text as UTC or pass JavaScript Unix milliseconds as ET seconds. The runtime does not read the clock, detect a timezone, resolve a city, load a dataset, or supply product settings. Sources: [Wasm wrapper](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/examples/configurable-chart/wasm/src/lib.rs), [angles and coordinate convention](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/astro/houses.rs), [runtime boundary](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/AGENTS.md).

`ChartValues` supplies effective configuration, convention revision, reference offset, speed reference, nineteen body/angle entries with longitude/speed/declination and sign progress, zodiac sectors, separate Whole Sign house sectors where applicable, twelve validated cusps, and requested/actual house systems. Angular values are degrees and speeds degrees/day. Preserve these returned values: do not project longitudes a second time or reconstruct sign and house tables from equal 30-degree assumptions. Placidus may return Porphyry fallback; overlapping cusp sets fail. True Sky retains tropical speeds, and angle speeds of zero mean not calculated. Sources: [chart result and calculation](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/chart.rs), [conventions](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/conventions.rs), [plugin result validator](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/chart.ts).

## Minimum website adapter specification

1. Capture the visit-start instant once. Initialization, data-download retries, settings changes and view switches use that captured instant until the user edits the chart. Do not recapture the clock after loading location/data. No clock timer, chart modes, persisted input or automatic refresh is introduced; this follows the [approved behavior resolution](https://github.com/AstrologyEngine/web/issues/6#issuecomment-6710681281).
2. Accept a resolved location result containing city identity/display fields, latitude, longitude, effective IANA timezone and real lookup provenance. An unavailable result must be explicit. Selection, alias treatment, unmapped-zone handling and fallback policy remain in [Choose inferred-city selection and fallback policies](https://github.com/AstrologyEngine/web/issues/16); this research does not select a fallback city or mapping dataset policy.
3. Derive local date, local time and the offset at that exact UTC instant using the effective timezone. Preserve the UTC instant as authority. A known instant maps to one civil time and offset even during a daylight-saving overlap; do not round-trip it through ambiguous civil-time parsing. Edited local birth input still follows the plugin resolver's ambiguity rules.
4. Match the plugin's current whole-second birth schema: normalize the single captured timestamp once to whole seconds, then derive UTC and all civil fields from that same value, with `timePrecision: "second"`. This is a concrete compatibility requirement of using that schema, not a library precision limitation. Retaining fractional seconds instead requires coordinated host schema/editor changes; do not silently calculate a different instant from the one represented by metadata.
5. Build a transient birth-details value compatible with the editor/snapshot contract. The existing schema requires place id/city/region/country/label, coordinates, timezone, offset, UTC, resolverVersion, atlasHash and timezoneDataVersion. Record truthful initializer/lookup identifiers and hashes; never pretend initialization ran through the plugin's server resolver or processed its atlas. Browser Intl does not establish a pinned tzdb version. If the website separates initializer provenance from edited-birth provenance, adapt host schemas together rather than inserting fake values.
6. Apply plugin defaults explicitly: Tropical, equal sign divisions, Ophiuchus false (effective engine value null), Whole Sign houses, `progressInSign` atmakaraka, Astrology enabled and Human Design disabled. Later settings changes use the same ordinary chart. Constellation divisions require True Sky and an explicit Ophiuchus enabled/disabled choice. No settings persistence is added.
7. Submit `{ generation, birth, settings }` to the calculation worker and publish only its validated snapshot for the current generation. Preserve recoverable loading/error states, retry behavior and generation-based rejection of stale results. The browser worker remains the execution host; the library remains pure and stateless.

Sources for requirements 3–7: [birth/settings schema and defaults](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/server/domain.ts), [birth resolver provenance](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/docs/birth-resolver-provenance.md), [worker](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/worker.ts), [snapshot validation](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/snapshot.ts). These specify adapter responsibilities, not permission to implement them in this planning map.

## Aspects and provenance ownership

The library owns positions, sign assignments, angles, cusps, fallback reporting and convention metadata. The plugin's pure `deriveAstrology(selected, tropical, method)` owns aspects, atmakaraka and intercepted signs. Reuse its selected-frame and tropical-basis calculations and preserve its aspect body-pair policy. Its aspects are derived over all returned pairs; the ten-planet eligibility set is for atmakaraka, not an aspect filter. The existing aspect angles/orbs are Conjunction 0/10, Semisextile 30/2, Sextile 60/6, Square 90/8, Trine 120/8, Quincunx 150/3 and Opposition 180/10, with applying/separating determined from tropical speeds. Do not move these policies into Rust merely to support initialization. Source: [derivation](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/chart.ts).

The host snapshot owns calculation id/generation, complete inputs/requested settings and asset/source identities: engine commit, supplementary policy-source commit, wrapper SHA-256, full-dataset SHA-256/fingerprint, selected-slice SHA-256 and returned convention revision. Location lookup/timezone provenance is separate from astronomical dataset identity. The worker verifies index, Wasm and slice hashes and validates output. Reusing assets preserves their actual pins; rebuilding requires updating verified identities together, not relabelling old bytes. Sources: [worker](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/worker.ts), [snapshot](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/snapshot.ts), [rebuild script](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/scripts/rebuild-engine.sh).

## Coverage, errors and Human Design

The shipped index advertises birth coverage from `1849-12-31T23:59:27.816001860Z` through `2149-12-20T23:58:50.816456371Z`. That is asset coverage, not a timeless library guarantee. The worker chooses the slice by UTC year and checks download identity. Annual slices include the previous year and padding, clipped to source coverage. Runtime chart admission also depends on finite-difference speed support (half-day samples on either side); retain generated fitted guard margins. Never clamp an invalid date or substitute coordinates/data silently. Sources: [index](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/static/engine/ephemeris/index.json), [segment preparation](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/examples/configurable-chart/prepare-segments.ts), [runtime guidance](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/AGENTS.md).

Keep invalid/unavailable location distinct at the initializer boundary. Preserve worker errors `INVALID_INPUT`, `DATA_UNAVAILABLE`, `DATA_INTEGRITY`, `OUT_OF_RANGE`, `CALCULATION_FAILED`, and `DESIGN_MOMENT_UNAVAILABLE`; the Wasm wrapper itself returns error strings and the runtime has invalid-input, out-of-coverage and evaluation failures. This research does not introduce a new typed Rust error API. Loading failures and integrity failures must not yield a plausible partial chart. Sources: [worker errors](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/worker.ts), [runtime errors](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/lib.rs).

Human Design already works with the same chart inputs. When enabled, the worker calls existing `design_moment_et`: find the backward tropical Sun crossing at birth Sun minus 88 degrees, then calculate the design chart using the returned **ET seconds directly** and the selected configuration/location. Do not convert ET through JavaScript Date or substitute “88 days earlier.” The search requires 89 days of public lookback coverage, so birth-date admission does not guarantee Human Design availability near the dataset's lower edge. Search errors and no crossing remain distinct underlying cases, even though the plugin intentionally presents its existing generic design-unavailable error. Preserve existing derived gates/channels/bodygraph policies and unchanged input semantics for edited natal charts. Sources: [design export](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/examples/configurable-chart/wasm/src/lib.rs), [search](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/search.rs), [lookback constant](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/src/coverage_window.rs), [plugin search adapter](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/design-search.ts), [HD derivation](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/src/lib/calculation/human-design.ts).

## Verification and handoff

A direct Bun execution of the **existing shipped Wasm** on 2026-11-07 used a fixed current-era instant (`2026-11-07T18:00:00Z`), explicit coordinates (41.85, -87.65), and plugin default chart settings. It returned nineteen entries, twelve cusps and `astrology-engine-conventions-v1`. Existing `design_moment_et` returned finite ET; calculating that design instant returned nineteen entries and twelve cusps. Coordinates were explicit test inputs, not an inferred-city policy decision. This is local execution evidence, not browser/CSP acceptance, native parity, or independent astronomical validation.

Required later implementation checks: fixed-clock one-capture initialization; consistent local/UTC/offset fields across midnight and DST overlaps; unknown-zone policy from its own decision; plugin-default/settings parity; invalid coordinates/settings; source and slice endpoints with speed padding; HD lower-edge lookback; index/Wasm/slice integrity and retry; stale-generation rejection; same snapshot for initial versus manually supplied identical inputs. Run the existing pinned full/slice and native/Wasm regression paths when rebuilding assets or changing the wrapper. Preserve metadata/sign tables exactly and compare numerical fields within the existing 1e-12 tolerance. Existing evidence reports 90 browser birth and 90 design full/slice cases with zero difference, but this session did not rerun that suite. Sources: [plugin calculation tests](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/tests/calculation.test.ts), [reported verification boundaries](https://github.com/AstrologyEngine/plugin/blob/8446c7b1388349a28daaabf27f13096b61142271/docs/calculation-provenance.md).

The library's own [AGENTS.md](https://github.com/AstrologyEngine/library/blob/b2bd547728f31a951a1afd78dfaa94225d8c152f/AGENTS.md) separates pure runtime from native preparation and host I/O and prohibits all Swiss Ephemeris execution, wrappers and derived validation artifacts. Preserve those boundaries and MPL notices/source obligations when redistributing existing artifacts. No Swiss Ephemeris was used here.

No library implementation issue is required for this finding. If a later verified gap needs library changes, coordinate through `AstrologyEngine/library` GitHub Issues using its current root/scoped instructions and verification workflows; an empty open-issue listing is not a separate tracker specification. The website integration ticket owns packaging, worker origin/CSP, birth-editor/resolver integration and provenance-schema adaptation. The city-policy ticket remains unresolved. Neither is resolved implicitly by this research.
